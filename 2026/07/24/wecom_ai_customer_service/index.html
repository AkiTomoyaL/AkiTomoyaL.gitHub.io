从 0 到 1：企业微信智能客服落地实践（LangGraph + RAG）

Created2026-07-24|Updated2026-07-24|人工智能
|Word Count:2.4k|Reading Time:7mins|Post Views:
不拒众流，方为江海

最近把一套企业微信智能客服从 0 做到能在群里真正跑起来：自动引导交材料、乱序也能归类、缺了会催，中间问业务问题也能答。

好耶！

这篇当项目复盘写一下：背景、通道怎么拆、Agent 怎么设计、后面 RAG 怎么补上去的。

一、先说清楚要解决什么

业务场景很直接：客户在企业微信群里交企业注册资料。

他们不会乖乖按表单顺序来，经常是：

  • 文字丢一堆：经营范围、手机号、股东姓名……
  • 图片甩一串：身份证、地址证明、手持证件、签名……
  • 中间还夹着问：「地址证明要什么？」「一定要公章吗？」

人工盯群的痛点也挺明显——反复催、容易漏、同类问题答到口干。

所以我要做的不是「闲聊机器人」，而是一个能办事的客服 Agent：

  1. 群机器人先推欢迎语和资料清单
  2. 文字 + 图片都能收，乱序也能填进结构化表单
  3. 缺什么催什么
  4. 中途提问走知识库，答完还能继续催材料
  5. 齐了就归档提交

我这边主要负责：企微通道接入、LangGraph 状态机、多模态收材料，以及后面的 RAG 意图分流。

二、做完之后大概长什么样

点 实际效果
入口 客户就在企微群里交材料、问问题，不用另开系统
收集 身份证、地址证明、手持证件、经营范围、董事/股东手机和签名等都能结构化收齐
多模态 文字提取 + 图片下载归档，支持多股东
流程 缺项自动催，齐了自动提交，少很多人工盯群
答疑 RAG + 意图分流，咨询和交材料不打架
稳定 回调异步、同群串行锁、会话状态能挂起恢复

三、整体架构

就两层：企微通道 + Agent 脑子。

技术栈大概是：

层级 用啥
通道 群机器人 Webhook + 自建应用回调
服务 FastAPI + 异步
Agent LangGraph（状态机 / interrupt / 会话记忆）
模型 DeepSeek
问答 意图路由 + 向量知识库 RAG
材料 企微媒体接口下载，按会话归档

四、企微通道：机器人推开场，自建应用扛后续

这块我拆成了两种出站方式，别混在一起。

1. 群机器人 Webhook：只负责「开场」

群里加机器人，拿 Webhook。服务端主动 POST 一段欢迎语，把注册资料清单一次性说清楚，比如：

  • 身份证正反面
  • 地址证明
  • 董事手持证件
  • 经营范围
  • 董事/股东手机号
  • 签名

分工记清楚：欢迎语和资料清单 = 群机器人主动推。后面的对话回复不走这条。

2. 自建应用：监听 + 收材料 + 催办 + 答疑

真正跟客户多轮互动的，是自建应用：

  • 配回调 URL / Token / EncodingAESKey，听群里说话
  • 收文字、收图片，按 MediaId 把材料下载下来
  • 缺项催办提醒：校验不齐时，由自建应用发回群里
  • RAG 答疑回复：客户问业务问题，也由自建应用回复

一句话：

机器人喊开场；自建应用负责听、收、催、答。

还有个很实际的点：企微回调有超时。大模型一推理好几秒，回调里同步跑 Agent 很容易被重试打爆。所以解析完立刻回成功，Agent 丢后台：

3. 图片怎么落下来

客户发图后，自建应用会：

  1. 调媒体接口把原图下下来
  2. 按群/会话分目录存
  3. 路径写进 Agent 状态，后面归类进表单字段

聊天里的一张图，最后就变成业务侧能用的材料文件。

五、Agent：多轮收材料的状态机

智能客服这事儿，靠一次 Prompt 不够，得是能挂起、能恢复的流程。

1. 每个群一条会话

thread_id = chat_id，主要记这些：

  • required_info：已经填了多少
  • pending_message / pending_image_path：这轮刚收到的
  • stage：走到哪了
  • current_intent：交材料还是提问

股东可以多人：

2. 流程长这样

collect_info

把「当前表单 + 用户最新文字/图片」喂给模型，让它输出合并后的 JSON；代码再做一层安全 merge（非空才覆盖，旧数据别丢）。一次发两个股东手机号 + 经营范围，也能拆开归位。

confirm

缺项用规则扫，催办清单稳一点。不齐就让自建应用把缺失项发到群里，再 interrupt 挂起；客户再发消息，同一会话接着跑。

pack

齐了提交业务系统，再在群里说一声收齐了。

六、几个让它别翻车的点

1. 同群必须串行

客户连拍好几张图，回调会并发进来。同一 chat_id 不加锁，状态很容易被写乱。所以每个群一把异步锁，消息排队处理。

2. 会话要能记住

靠 checkpointer 按群存进度。挂起之后还能从断点继续，客户不用从头交一遍。

3. 模型和代码各干各的

  • 模型：懂自然语言、猜图片大概是啥、把话说得像人
  • 代码：merge、缺项检查、加锁、回调超时保护

理解交给模型，正确性交给工程，线上才稳一点。

七、后面补上 RAG：既能办事，也能答疑

收材料跑通之后，客户还是会问：

「地址证明要什么？」「一定要公章吗？」「大概多久？」

如果全塞进填表节点，要么乱填 JSON，要么爱答不理。所以后面加了 意图分流 + RAG。

1. 入口先分流

  • submit_info：在交材料 / 「好的发你了」这类配合
  • ask_question：在问怎么做、要什么、多久……

纯图片基本直接当交材料；刚催完材料时，短回复也更偏向补充资料。

2. 答完还能接着催

RAG 节点查完知识库回复，同时能看到当前还缺啥，于是答疑结尾可以很自然地接一句催办：

……水电费单一般是可以的哈。对了，您股东张三的签名好像还没发，方便时拍一张发群里就行。

这类回复走自建应用发出去，不是机器人 Webhook。

3. Prompt 拆开写

  • 填表：态度冷酷眼睛，只输出结构化 JSON 内容
  • 问答：口语一点，像真人秘书，无非就是模拟真人对话

分流之后，咨询不会污染填表；知识库有依据；答完还能推主流程，体验顺很多。

八、串起来看一整条链路

  1. 建群，拉上机器人和自建应用
  2. 群机器人推欢迎语 + 注册资料清单
  3. 客户发文字（股东、手机号、经营范围）→ 自建应用收到 → 填表 → 自建应用催剩余项
  4. 客户问「地址证明要什么」→ RAG → 自建应用回答，顺带催签名
  5. 客户连发身份证、手持照、签名等图 → 下载归档 → 继续填表
  6. 校验通过 → 提交业务系统 → 群里确认收齐

客户全程都在企微群里，不用学新系统。

九、项目全链路实现

  1. 把「群内收材料 + 答疑」拆成能落地的 Agent 流程
  2. 企微接入：机器人 Webhook 开场；自建应用监听、收材料、催办、答疑
  3. LangGraph 多轮状态机：挂起、恢复、缺项校验
  4. 文字和图片统一进结构化表单
  5. RAG：意图分流 + 知识库问答，并和催办串起来
  6. 工程上：异步回调、同群串行锁、会话记忆和日志

能力上大概覆盖：大模型落地 / Agent 工作流 / 企微集成 / RAG / 异步后端。

十、一点复盘

比较管用的顺序：

  1. 先把企微通道打通
  2. 先保证填表主流程，再叠加 RAG
  3. 关键正确性用规则兜底，别全押 Prompt
  4. 问答和填表 Prompt 分开写

后面还能继续加：图片前置 OCR/VLM 分类、高风险转人工、知识库命中率监控之类的。

打通企业微信是最麻烦的，限制太多。

写在最后

这个项目对我来说，是一次比较完整的 AI 落地：

  • 企微上真实地听得到、收得到、回得了
  • LangGraph 把多轮业务收成可控状态机
  • RAG 让它既能办事，也能答疑

行有所思，学有所得。—— AkiTomoyaL
