千川自动化投流项目：从素材上传到 ROI 降档的全链路实践

Created2026-08-19|Updated2026-08-19|人工智能
|Word Count:3.3k|Reading Time:10mins|Post Views:

最近又折腾了一套千川自动化投流工具。说白了，就是把原本要在后台反复授权、传素材、找商品、建计划、盯消耗的流程，尽量收成一条能自己跑的链路。

不拒众流，方为江海

好耶！

这篇按项目复盘写一下：素材怎么进来，Token 怎么管，商品 ROI 怎么算，计划怎么自动创建，以及后面为什么要做 1.5 小时无消耗自动降 ROI。

一、先说清楚要解决什么

千川投流这件事，真正麻烦的不是“点一下创建计划”，而是前后有一串很碎的动作：

  • 授权账户多，抖店账户、工作台账户、千川投放账户要分清；
  • 素材多，原图要进图文库，上架图要进图片库；
  • 商品多，商品 ID、线上商品编码、款式编码要能对上；
  • ROI 不是拍脑袋填，至少要结合成本、退款率和保本线；
  • 计划创建后还要看消耗，没有消耗时要及时降档；
  • 接口偶发超时、Token 过期、素材重复，都要能继续跑。

如果全靠人工做，很容易变成复制粘贴体力活。更麻烦的是：错一个商品 ID 或者素材 ID，后面计划可能就跑偏了。

所以这个项目的目标很明确：

  1. 扫描本地 / 网盘素材目录，识别型号文件夹；
  2. 上架图上传到图片库，原图创建图文素材；
  3. 自动维护多 Token 和千川账户映射；
  4. 读取低价商品表和店铺商品表，生成商品 ID - 款式编码 - ROI 映射；
  5. 自动匹配商品、账户、素材和抖音号；
  6. 支持 dry run 预检、正式投流和增量投流；
  7. 计划 1.5 小时无消耗时，目标 ROI 降低 10%，最低降到 1.5。

我这边主要关注的是：图库素材状态流转、OAuth 多 Token 管理、商品 ROI 映射、自动投流任务编排，以及 ROI 自动降档规则。

二、整体结构

先放结构图，整条链路基本都在这里了。

项目本身是一个 Flask Web 管理端，后面用 SQLite 存 Token、素材库状态、自动投流计划和运行日志。代码里大概可以分成这几块：

文件 / 目录 负责什么
app.py Flask 路由、Token 管理、图库任务、自动投流、ROI 巡检、千川接口封装
db.py SQLite 表结构和状态读写，存 tokens、素材状态、投流记录、日志
gallery_uploader.py 素材扫描、远端去重、上架图上传、原图创建图文素材
low_price_label/merge_break_even_roi.py 合并店铺商品表和低价商品表，计算保本 ROI
templates/ 管理页：Token、图库、素材、商品、计划、自动投流看板
oceanengine_qianchuan_label_12_docs/ 千川接口文档和本地接口规格

它不是一个很重的中台，更像是一个面向运营动作的“投流工作台”：能看、能跑、能停、能复盘。

三、Token：多授权别互相覆盖

千川接口绕不开 OAuth。刚开始只想着拿到 token 就能调接口，后面发现真正麻烦的是多账户管理：

  • 新授权不能覆盖旧授权；
  • 每条授权要知道它对应哪些抖店和千川账户；
  • access token 过期要自动刷新；
  • 某个账户创建计划时，要找到它所属的 token；
  • 授权 URL 如果带错参数，可能只授权素材权限，后面拿不到投放账户。

所以代码里把 Token 管理拆成了独立模块：

管理端提供了几类接口：/token/list、/token/select、/token/remove、/token/refresh_info。
自动投流时再通过千川 advertiser_id 反查对应 token，避免“当前活跃 token”切错导致接口调用错账户。

Token 这块一定要当基础设施处理。它看起来不起眼，但它一挂，后面素材上传、计划创建、消耗拉取全都跟着停。

四、素材线：扫描和上传必须解耦

素材上传不是“遍历文件夹然后一股脑传上去”。我这里拆成了两步：

这样做是为了稳定。
图库服务器和网盘目录并发能力都不算强，如果扫描和上传混在一起，很容易跑到一半崩掉。拆开后，扫描只列目录，上传才读取具体图片。

1. 型号文件夹怎么识别

目录里只要同时有“上架图”和“原图”，就会被识别成一个可上传型号。
含“套图”的节点会作为套图组目录，最后抽出款式编码，比如 BD339D 这种。

素材状态会落到素材库里，大概包含：

  • 品类；
  • 套图组；
  • 款式编码；
  • 原图列表；
  • 上架图列表；
  • 每个千川账户下的图片素材 ID；
  • 每个千川账户下的图文素材 ID；
  • pending / done / error / missing 等状态。

2. 上架图和原图走两条路

项目需求里写得很清楚：

原图对应图文库，上架图对应图片库。

所以实现里也是这样：

  • 上架图：单张上传到图片素材；
  • 原图：先把图传成图文内图片，再创建一个图文素材；
  • 图文创建完成后，可以清理图片库里临时的“图文中间图”，避免图片库越堆越乱。

素材命名也做了统一，类似：

后面自动投流匹配素材时，就靠这些名字里的款式编码去找。

3. 几个实际坑

千川素材接口有不少细节：

  • 图片素材单张有大小限制，代码里对图文内图片做了预处理；
  • 千川端可能已经有同名素材，所以上传前要拉远端素材库做去重；
  • 老版本命名的素材要能回填状态，不然会重复上传；
  • access token 过期时，上传器要能刷新后重试；
  • QPS 要控住，代码里对素材上传、素材查询都做了简单节流。

素材线跑稳以后，后面的投流才有基础。否则自动创建计划时一直提示缺素材，整个链路就会变成“自动报错系统”。

五、商品线：保本 ROI 怎么算

商品映射这块主要读两个表：

  • 店铺商品资料：拿商品 ID、店铺名、商品名称、线上商品编码；
  • 低价引流表：拿款式编码、零售综合成本、抖音定价。

项目里退款率先固定为 **15%**。
抖音定价按低价表里的字段走，实际整理数据时会按折扣价区间最低价再减 10 做定价口径。

保本 ROI 公式大概是：

合并后会输出几张表：

  • 商品ID_款式编码_保本ROI映射表.csv
  • 商品ID_款式编码_投流映射表.csv
  • 商品ID_款式编码_投流映射异常.csv

自动投流用的是完整投流映射表：所有店铺商品都会尽量保留，低价表命中的商品再补上保本 ROI。
这样后面即使不是低价款，也能被投流链路识别，只是 ROI 信息可能为空，需要人工确认。

六、自动投流：先预检，再正式跑

自动投流的核心函数会先构建映射表，再按“店铺 + 商品 ID”分组。每组里可能有多个款式编码。

正式创建计划时，还会统一处理这些参数：

  • 预算不能低于 300；
  • 默认目标 ROI 可由页面输入；
  • 创意标题固定一版，避免每次乱填；
  • 开启 QCPX_MODE_ON；
  • 开启 AIGC 动态创意；
  • 创建失败会写日志，计划互斥时尝试接管已有计划；
  • 已创建计划如果发现新素材，会走 update 补充素材。

管理端接口也拆得比较细：

  • /auto_delivery/run：预检或正式投流；
  • /auto_delivery/incremental/start：增量投流，按间隔循环扫新增素材 / 商品；
  • /auto_delivery/stop：停止当前投流任务；
  • /auto_delivery/status：查看 created 记录、日志和 ROI 监控状态；
  • /qianchuan/uni_aweme/ad/create：创建全域投放计划；
  • /qianchuan/uni_aweme/ad/update：编辑全域投放计划。

我比较喜欢这里的 dry run。
因为投流是带预算的动作，先预检一遍能看到哪些商品缺素材、哪些账号无商品、哪些抖音号没授权，确认没问题再正式跑，心里踏实很多。

七、ROI 降档：1.5 小时无消耗就别硬等

需求里后来又加了一个功能：

目标 ROI 如果每 1.5 小时计划没有消耗，就修改 ROI 降低 10%。比如目标 ROI 3，1.5 小时后没有消耗就调整为 2.7，以此类推，最后最低调整到 1.5。

代码里对应的常量也很直白：

巡检时会先拉计划列表，取 stat_cost 和当前 roi2_goal：

  • 如果 stat_cost > 0，说明计划已经有消耗，停止自动降档；
  • 如果没有消耗，按 90% 计算新 ROI；
  • 如果已经低于或等于 1.5，停止降档；
  • 如果接口失败，记录错误并延迟重试；
  • 每次调整都会写入 ROI 调整历史。

这块不是为了搞复杂策略，而是解决一个很实际的问题：
计划挂着没消耗时，人盯着后台反复刷新也没意义。既然动作明确，就让程序先把第一层机械调整做掉。

八、几个让我觉得必须做的细节

1. 状态一定要落库

素材上传、计划创建、ROI 调整都不是一次性动作。
任何一步失败，都要知道失败在哪、能不能重试、重试会不会重复创建。

2. 日志要给人看

自动化任务跑失败时，最怕只看到一句“失败”。
看板里最好能看到：当前商品、当前素材、当前账户、调用哪个接口、返回什么错误。

3. 接口要节流和重试

千川接口偶尔会返回临时错误，图库服务也可能慢。
代码里对读取、写入、素材接口分别做了 timeout、retry 和节流，不然长任务很容易半路断。

4. 人工入口不要删

自动化再顺，也要给运营人员留手动查看和干预的入口。
尤其是投流这种带预算的东西，程序负责跑重复流程，人负责最后判断。

九、项目全链路实现

  1. Flask Web 管理端：Token、图库、素材、商品、计划、自动投流看板；
  2. OAuth 多 Token：授权回调、账户映射、自动刷新、按千川账户反查 token；
  3. 素材扫描：本地 / 网盘目录识别型号文件夹，只扫描入库不上传；
  4. 素材上传：原图创建图文素材，上架图上传图片素材；
  5. 素材去重：远端同名检查、旧命名回填、图文中间图清理；
  6. 商品映射：店铺商品表 + 低价商品表，生成商品 ID、款式编码、保本 ROI；
  7. 自动投流：匹配店铺、账户、商品、抖音号、图片素材和图文素材；
  8. 计划管理：dry run 预检、正式创建、已有计划补素材、增量投流；
  9. ROI 监控：1.5 小时无消耗降 10%，最低 1.5，有消耗即停止；
  10. 运行记录：计划、日志、ROI 调整历史都落 SQLite，方便复盘。

能力上大概覆盖：自动化后台 / 第三方 API 集成 / OAuth Token 管理 / 素材管线 / 定时任务 / 业务规则引擎。

写在最后

这个项目本质上不是为了炫技，而是把一堆很碎、很容易出错、又每天都要重复做的投流动作串起来。

做完之后最明显的感觉是：
素材、商品、ROI、计划状态终于不是散在几个表和几个后台里了，而是能沿着一条链路追下去。

当然后面还能继续加，比如更细的失败重试、素材质量评分、计划效果复盘、按品类自动选择投放模板之类的。

但第一阶段能做到自动扫描素材、自动上传图文和图片、自动建计划、自动看消耗、自动降 ROI，就已经能省掉不少机械操作了。

行有所思，学有所得。—— AkiTomoyaL
