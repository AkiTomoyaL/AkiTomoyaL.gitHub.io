电动自行车智能预审系统：OCR + CV 的资料合规初筛实践

Created2026-08-01|Updated2026-08-01|人工智能
|Word Count:2.2k|Reading Time:6mins|Post Views:

这次整理的是一个电动自行车智能预审系统。核心想法很直接：把人工审核前面那些重复、机械、容易漏看的检查，先让 OCR + CV 帮忙筛一遍。

不拒众流，方为江海

好耶！

这篇按项目复盘写一下：资料怎么分类，证件怎么识别，车辆部件怎么比对，最后怎么进合规规则引擎。

一、为什么要做预审

电动自行车报审材料里，最常见的问题不是特别复杂，而是特别杂：

  • 合格证、发票、身份证、查验表经常混在一起；
  • VIN、品牌型号、电机功率、电池类型这些字段需要人工对；
  • 整车图、部件图、VIN 码图片质量参差不齐；
  • 有些车可能存在改装风险，比如电池、电机、控制器等关键部件不一致；
  • 缺材料时，人工还要来回退补。

如果所有材料都直接进人工审核，效率会很低。
所以预审系统不做最终裁定，它更像一个前置分拣员：

  1. 先把材料接住并分类；
  2. 能 OCR 的先抽字段；
  3. 能视觉检测的先定位部件；
  4. 规则能判的先判；
  5. 不确定的再拦截给人工复核。

我的理解是：预审系统不是替代人工，而是把“明显通过、明显缺失、明显可疑”的材料先分出来，让人工集中处理真正需要判断的部分。

二、整体结构

先放结构图，整套流程基本按“材料分类 -> OCR / CV 两条线 -> 规则引擎 -> 预审结果”来走。

从入口看，材料会先进入预审系统，然后分成两类：

材料类型 处理方式
合格证 / 发票 / 身份证 / 查验表 OCR 解析，结合 PaddleX + 正则做结构化字段提取
整车图 / 车辆部件图 / VIN 码图片 CV 检测、关键区域定位、部件实例分割和相似度比对

两条线最后都会汇到 FastAPI 预审路由，再交给合规规则引擎统一判断。

三、证件线：OCR 先把字段拿出来

证件材料主要解决的是“文字信息能不能对上”。

流程大概是：

OCR 只负责把文字读出来还不够。
真正落到业务里，还要把一堆文本变成稳定字段，比如：

  • VIN；
  • 电机功率；
  • 电池类型；
  • 品牌；
  • 型号；
  • 发票信息；
  • 证件号；
  • 查验表关键项。

这里我会更倾向于 “OCR + 规则” 混合处理。
模型负责识别，正则和字段规则负责收口，不然很容易出现读出来一大段字，但系统不知道哪个字段该往哪里填。

一个细节：字段置信度要留下

有些字段 OCR 结果会很像，但差一个字符就完全不是一回事，尤其是 VIN。
所以结构化时最好保留原始识别文本、清洗后的字段、置信度和来源图片，后面人工复核会轻松很多。

四、图像线：先找关键部件，再做一致性比对

车辆图片这条线，重点不是“看图好不好看”，而是看关键部件是否和标准信息一致。

结构图里的 CV 链路是：

这里比较关键的是两层：

  1. 检测定位：先把整车、VIN、关键部件区域找出来；
  2. 相似度比对：把部件特征和标准库里的部件向量做比较。

最后根据相似度分数判断是否存在疑似改装：

  • 相似度正常：部件一致性通过；
  • 相似度偏低：打上改装风险标记；
  • 图片质量太差：不能硬判，应该退补或转人工。

视觉模型最怕“看不清还硬判”。预审系统宁愿输出“需要复核”，也不要把低质量图片包装成高置信结果。

五、FastAPI 预审路由：把模型结果交给规则

OCR 和 CV 的结果最终会进入 FastAPI 预审路由。

我比较喜欢把这里当成一个“汇总口”：

  • 接收证件结构化字段；
  • 接收车辆图像检测结果；
  • 接收相似度评分和风险标记；
  • 统一组装成规则引擎能理解的数据结构；
  • 生成预审记录。

真正决定预审状态的是后面的合规规则引擎，主要校验四类问题：

校验项 看什么
证件与车辆信息一致性校验 VIN、品牌型号、发票 / 合格证信息是否对得上
参数合规校验 电机功率、电池类型等关键参数是否符合要求
改装风险校验 部件相似度是否异常，是否存在疑似改装
资料完整性校验 必传材料是否齐全，图片是否可识别

这样拆完之后，模型和规则的边界会清楚很多：

  • 模型负责“看见”和“抽取”；
  • 规则负责“判断”和“分流”。

六、预审结果怎么分流

规则引擎输出的结果大概分三类：

这里有个很实际的点：
预审系统的价值，不只是“自动通过”，更重要的是把退补原因说清楚。

比如：

  • 缺少发票；
  • VIN 码图片无法识别；
  • 合格证型号与车辆图像疑似不一致；
  • 电池部件相似度偏低，建议人工复核；
  • 电机功率字段缺失或疑似超标。

有明确原因，申请人补材料才不会乱补，审核人员也能快速定位问题。

七、几个让系统更稳的点

1. 先分类，再识别

材料没分类就直接 OCR，很容易把身份证当发票，把查验表当合格证。
先做材料接收与分类，后面的识别规则才有上下文。

2. VIN 要重点保护

VIN 是证件线和图像线连接的关键字段。
OCR 抽 VIN、VIN 码图片识别、证件信息一致性校验都绕不开它，所以这里要保留原图、原始文本和清洗结果。

3. 规则别全塞进模型

参数合规、资料完整性、是否退补，这些更适合规则引擎处理。
模型可以帮忙识别和分类，但最后判断最好可解释、可追溯。

4. 预审记录要完整

每次预审都应该生成记录：材料、字段、相似度、命中的规则、最终结果。
后面无论是人工复核，还是回看误判，都要靠这些记录。

八、项目全链路实现

  1. 申请人提交上牌材料；
  2. 预审系统入口接收材料；
  3. 材料接收与分类；
  4. 证件线：OCR + PaddleX + 正则抽取 VIN、电机功率、电池类型、品牌型号等字段；
  5. 图像线：车辆关键区域检测、部件实例分割、特征向量提取和标准库比对；
  6. FastAPI 预审路由汇总结构化结果；
  7. 合规规则引擎做一致性、参数、改装风险和完整性校验；
  8. 输出预审结果；
  9. 自动通过、退回补正，或者拦截转人工复核；
  10. 生成预审记录。

能力上大概覆盖：OCR 结构化抽取 / 机器视觉检测 / 部件相似度检索 / FastAPI 服务 / 合规规则引擎。

写在最后

这个系统比较有意思的地方在于，它不是单纯做 OCR，也不是单纯做目标检测，而是把两条线合到一个业务判断里。

证件线解决“资料上写了什么”；
图像线解决“车和部件看起来是不是对”；
规则引擎解决“这些信息放在一起合不合规”。

后面如果继续优化，我会优先补三件事：

  1. 标准部件向量库持续扩充；
  2. 人工复核结果反哺模型阈值；
  3. 对低质量图片做更明确的退补提示。

预审这类项目，最怕模型单点炫技。
真正有用的是：能把材料收住、字段抽准、风险说清楚，然后把人工从重复检查里解放一点出来。
