RAG项目从0到1：从文档切片到Milvus检索的全链路实践

Created2026-09-01|Updated2026-09-01|人工智能
|Word Count:5.2k|Reading Time:17mins|Post Views:
不拒众流，方为江海

最近又系统看了一遍 RAG 项目的完整链路。感觉 RAG 这东西看起来就是“把文档丢进去，然后问答”，实际落地时每一步都能踩坑：文档怎么切、向量怎么存、检索怎么召回、答案怎么不胡说，最后还得能评估、能上线、能维护。

好耶！

这篇就按项目复盘的方式写一下：如果要从 0 到 1 做一个 RAG 知识库问答项目，完整链路应该怎么拆。
其中向量数据库这块，我会重点用 Milvus 来讲一下实践思路。Milvus 主要负责向量存储、索引和过滤检索；后面的重排序、Prompt 组装和 LLM 生成，是 RAG 在线链路里的后续阶段。

一、这算不算一篇 RAG 从 0 到 1 的文档？

算，但更准确地说，它是一篇 RAG 项目全链路路线图。

因为一个完整 RAG 项目不只是“调一个大模型接口”，它至少要覆盖下面几件事：

阶段 核心问题
文档处理 PDF、Word、网页、表格怎么解析，元数据怎么保留
文本切片 chunk 多大合适，标题层级怎么保留，父子块怎么设计
向量入库 embedding 怎么选，向量库怎么建 schema 和索引
在线检索 关键词、向量、过滤条件怎么组合，召回多少合适
重排序 初召回结果怎么二次排序，避免相似但不相关
生成回答 Prompt 怎么约束引用，怎么处理“知识库没有答案”
评估优化 怎么看命中率、答案准确性、延迟和成本
工程部署 增量更新、权限隔离、日志监控、灰度发布怎么做

所以我理解的 RAG 从 0 到 1，不是单个 demo，而是一条这样的生产链路：

RAG 的核心不是“让模型变聪明”，而是让模型回答前先去查可靠资料。它解决的是知识更新、私有数据、可溯源回答这三个问题。

二、先说清楚 RAG 要解决什么

很多业务场景里，大模型原本有三个硬伤：

  • 不知道私有资料：公司制度、产品文档、客户 SOP、接口说明，它训练时没见过；
  • 知识会过期：业务规则今天改，模型不可能自动同步；
  • 回答没依据：即使答对了，也很难说明它参考了哪一段资料。

RAG 的思路就比较朴素：

  1. 先把业务文档整理成知识库；
  2. 用户提问时，先从知识库里检索相关片段；
  3. 把检索结果塞进 Prompt；
  4. 让大模型基于这些片段回答；
  5. 最后返回答案和引用来源。

换句话说，RAG 项目做的是一套“先查资料再回答”的系统。

这也是为什么我觉得它特别适合这些场景：

  • 企业内部制度问答；
  • 产品手册 / API 文档问答；
  • 客服知识库；
  • 合同、招标文件、政策文件查询；
  • Agent 执行业务前的知识补全；
  • Text2SQL 前的表结构和指标口径检索。

三、知识库构建：别急着向量化

很多 RAG demo 会直接把一段文本切块、embedding、入库，然后就开始问答。
但真实项目里，第一步其实是文档解析。

1. 文档解析要保留结构

RAG 里最怕一种情况：原文档结构很清楚，解析完变成一坨纯文本。

比如一个产品手册原本长这样：

如果解析后标题层级丢了，模型检索到“退款”相关片段时，就很难判断这段到底属于哪种订单。

所以解析时建议尽量保留：

  • 标题层级；
  • 段落顺序；
  • 表格内容；
  • 图片 / 附件说明；
  • 页码、章节、文档来源；
  • 更新时间、业务线、权限范围等元数据。

这些元数据后面会非常有用。比如检索时可以过滤“只查客服知识库”“只查 2026 年后的文档”“只查某个产品线”。

2. 表格不要粗暴转文本

表格是 RAG 里很容易翻车的部分。

比如价格表、字段说明、接口参数表，如果直接按行拼成文本，模型有时会把列关系搞混。更稳的做法是：

  • 简单表格：转成 Markdown table；
  • 参数表：保留字段名、类型、是否必填、说明；
  • 财务 / 统计类表格：必要时单独走结构化查询，不要硬塞进普通 RAG；
  • 大表格：拆成小表或按业务主键建索引。

RAG 不是万能文件阅读器。结构化数据太强的场景，比如明细账、库存表、订单表，很多时候 Text2SQL / 数据库查询会比向量检索靠谱。

四、文本切片：chunk 决定检索上限

切片是 RAG 里最不起眼、但影响特别大的环节。

切得太大：

  • 一个 chunk 里混了太多主题；
  • 检索命中后上下文浪费；
  • Prompt 成本变高；
  • 重排序也更难判断相关性。

切得太小：

  • 语义不完整；
  • 答案需要跨多个片段拼；
  • 模型拿到的上下文断断续续；
  • 很容易答得像“只看了半句话”。

1. 推荐递归切分

这样切出来的片段通常比固定字符数硬切更稳。

2. Parent-Child 方案很实用

还有一个我比较喜欢的方案：Parent-Child Chunk。

简单说就是：

  • child chunk：切得小一点，用来做精准召回；
  • parent chunk：保留更完整的上下文，用来喂给模型生成。

比如用户问“预售订单退款多久到账”，child chunk 可能只命中一小段规则；但最终给模型的 parent chunk 可以包含整个“预售订单退款规则”小节，回答会完整很多。

五、Embedding：别只看榜单

Embedding 模型负责把文本转成向量。
向量越能表达语义，后面检索越容易命中正确内容。

选 embedding 模型时，我会看几个点：

  • 中文效果怎么样；
  • 维度是多少；
  • 最大输入长度；
  • 成本和延迟；
  • 是否支持私有化部署；
  • 和向量库索引参数是否匹配；
  • 是否需要 query / passage 不同前缀。

业务早期可以先用一个稳定模型跑通链路，不要一开始就陷入模型横评。
等检索样本积累起来，再拿真实问题做评估：同一批 query，看看 top-k 是否命中正确答案片段。

六、向量数据库：为什么这里用 Milvus

向量数据库的作用是：存储 embedding，并支持高效相似度检索。

先把边界说清楚：Milvus 不负责替你生成答案，也不等于 reranker。
它在 RAG 里主要承担“把候选知识片段又快又准地召回”的角色。召回之后，通常还会接一层 reranker，再把筛好的上下文交给 LLM 生成回答。

如果只是本地 demo，FAISS、Chroma、SQLite 扩展都能玩。
但如果考虑工程化，比如数据量上来、要服务化、要增量更新、要过滤元数据、要调索引参数，Milvus 会更适合做一个正式知识库底座。

Milvus 适合 RAG 的点主要有：

  • 支持向量字段和标量字段一起建模；
  • 支持 HNSW、IVF_FLAT 等索引；
  • 支持按元数据过滤；
  • 支持批量插入和搜索；
  • 可以本地 Docker 启动，也能往集群扩；
  • Python SDK 上手比较直接。

1. RAG 里建议这样设计 Schema

不要只存一个 embedding 和 text。
真正线上用时，最好把溯源和过滤字段也放进去。

这样后面就能做：

  • 只查某个业务分类；
  • 返回答案时带来源；
  • 文档更新时按 doc_id 删除旧 chunk；
  • child chunk 命中后回填 parent chunk；
  • 分析哪些文档经常被命中，哪些从来没被查到。

3. 插入 chunk

入库时要保证文本、向量、元数据一一对应。

我建议入库前先做一层校验：

  • 空文本不要入库；
  • 太短的目录、页眉、页脚不要入库；
  • embedding 失败的 chunk 单独记录；
  • 同一个 doc_id 重建时，先删除旧 chunk 再插入新 chunk；
  • 每次构建保留批次号，方便回滚。

4. 检索时加过滤条件

不要所有知识混在一起查。
比如客服问题只查客服知识库，技术问题只查技术文档，权限不同的人只查自己能看的资料。

limit=20 不代表最后把 20 个片段都塞给模型。
一般是先多召回一点，再交给 reranker 二次排序，最后挑 3 ~ 8 个高质量片段进 Prompt。

Milvus 这块别只当“向量存储”用。Schema、索引、过滤条件、增量更新、命中日志，才是它在 RAG 项目里真正发挥作用的地方。

七、在线检索：别只靠向量相似度

向量检索擅长语义相似，但它不是所有问题都稳。

比如用户问：

「BD339D 这个款式的退款规则是什么？」

BD339D 这种编码对向量模型来说不一定有语义。
如果只靠向量检索，可能会召回一堆“退款规则”，但漏掉这个精确款式。

所以线上 RAG 通常会做 混合检索：

1. Query Rewrite

用户问的问题经常很短：

  • “这个怎么处理？”
  • “要多久？”
  • “能退吗？”

如果直接拿去检索，效果通常一般。

2. Reranker 很关键

初召回阶段宁愿多召回一点，然后用 reranker 精排。

向量 top-k 经常会出现这种情况：

  • 语义很像，但不是同一业务；
  • 关键词命中了，但上下文不相关；
  • 同一文档多个 chunk 都被召回，内容重复；
  • 老版本文档和新版本文档同时出现。

reranker 可以把“问题 + 候选片段”放在一起重新打分，比单纯向量距离更贴近最终问答效果。

最后进 Prompt 的片段，我一般会做几层处理：

  1. 去重；
  2. 按分数排序；
  3. 优先保留新版本；
  4. 控制总 token；
  5. 带上来源信息。

RAG 的生成 Prompt 不能写成“请根据以下资料回答”。
这太宽了，模型很容易一边参考资料，一边自己补常识。

1. 要允许它说“不知道”

RAG 项目上线后，最危险的不是模型不会答，而是它没查到还硬答。

所以 Prompt 里一定要明确：

  • 没有依据就说没找到；
  • 资料冲突时说明冲突；
  • 不要把推测说成制度；
  • 高风险问题可以转人工；
  • 答案要尽量带来源。

2. 引用不是装饰

如果是企业内部知识库，引用来源特别重要。
它能让用户知道答案来自哪份文档，也方便后面排查问题：

  • 是文档过期？
  • 是切片错了？
  • 是检索没命中？
  • 是 reranker 排错了？
  • 还是模型生成时理解歪了？

RAG 的可维护性，很大一部分就靠这条溯源链路。

九、评估：不要只靠感觉

RAG 很容易出现一种错觉：
自己随便问几个问题，感觉答得还行，就以为系统能用了。

但真实上线后，用户问法会特别散。
所以最好准备一批评估集：

指标 看什么
Recall@K 正确片段有没有被召回
MRR 正确片段排得靠不靠前
Answer Accuracy 最终答案是否正确
Faithfulness 答案是否真的来自参考资料
Latency 检索、重排、生成分别耗时多少
Cost embedding、rerank、LLM 成本
No-answer 查不到时是否能拒答

我觉得最小可用评估集可以这样做：

  1. 从真实业务问题里整理 50 ~ 100 个 query；
  2. 人工标注每个问题应该命中的文档片段；
  3. 每次调整 chunk、embedding、索引、reranker 时跑一遍；
  4. 记录 top-k 命中率和最终答案质量；
  5. 发现坏例子就归类：解析问题、切片问题、检索问题、生成问题。

RAG 优化不要全靠调 Prompt。很多回答不好，其实是前面检索没把正确资料拿回来。资料没进 Prompt，模型再聪明也只能猜。

十、工程化：上线后才是真正开始

如果只是 demo，RAG 很快能做出来。
但如果要长期用，工程化部分不能省。

十一、RAG 项目全链路实现

如果把这篇收成一张 checklist，大概就是：

  1. 明确业务边界：知识库问答、客服答疑、文档检索，还是 Agent 辅助决策；
  2. 文档解析：保留标题、段落、表格、页码、来源和更新时间；
  3. 清洗规则：去掉页眉页脚、目录噪音、重复内容和空片段；
  4. 切片策略：优先递归切分，复杂场景用 Parent-Child；
  5. Embedding：先选稳定模型跑通，再用真实 query 评估；
  6. 向量库：Milvus 建 collection、schema、索引和元数据字段；
  7. 入库流程：批量插入、失败重试、doc_id 增量更新、批次记录；
  8. 在线检索：query rewrite、关键词 + 向量混合检索、权限过滤；
  9. 重排序：reranker 精排、去重、控制上下文长度；
  10. 生成回答：Prompt 约束引用、允许拒答、资料冲突要说明；
  11. 评估体系：Recall@K、答案准确性、faithfulness、延迟、成本；
  12. 工程部署：日志、监控、反馈闭环、灰度发布、文档版本管理。

能力上大概覆盖：文档工程 / 向量数据库 / 检索系统 / Prompt 设计 / LLM 应用评估 / 后端工程化。

十二、几个我觉得最容易踩的坑

1. 文档没处理好，后面全白搭

RAG 的数据质量特别重要。
如果解析出来的文本本身就是乱的，后面 embedding、检索、rerank 都是在处理噪音。

2. chunk 不是越大越好

大 chunk 看起来信息全，实际经常召回不准。
小 chunk 看起来精准，又容易丢上下文。Parent-Child 方案就是为了解这个矛盾。

3. 向量检索不是全文搜索的替代品

编号、型号、人名、字段名、接口名这些精确词，关键词检索仍然很重要。
RAG 线上效果想稳，混合检索基本绕不开。

4. 不要忽略“查不到”的体验

知识库没答案时，要让系统明确拒答或转人工。
否则用户最怕的不是“它不知道”，而是“它不知道但还很自信”。

5. 评估集要尽早建

没有评估集，就很难判断一次优化到底是变好了还是只是换了一种错法。
RAG 调参最好每次都有数据兜底。

写在最后

RAG 项目看起来门槛不高，真正做起来才会发现，它不是一个单点技术，而是一条链路。

文档解析决定知识能不能进来；切片决定检索能不能命中；Milvus 这类向量数据库决定知识能不能稳定查；reranker 决定上下文质量；Prompt 和评估决定最后答案能不能让人信。

所以如果从 0 到 1 做 RAG，我会按这个顺序来：

  1. 先把小规模知识库跑通；
  2. 再补文档解析和切片质量；
  3. 用 Milvus 把向量检索工程化；
  4. 加混合检索和重排序；
  5. 最后做评估、日志和增量更新。

不要一上来就追求“大而全”。
先让一条真实业务问题能从文档里查到依据、生成答案、带回引用，这条链路跑通了，后面才有优化空间。

行有所思，学有所得。—— AkiTomoyaL
