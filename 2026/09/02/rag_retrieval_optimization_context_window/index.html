RAG检索优化：上下文扩展为什么比单纯调chunk更有效

Created2026-09-02|Updated2026-09-02|人工智能
|Word Count:4.2k|Reading Time:13mins|Post Views:
不拒众流，方为江海

上一篇写了 RAG 从文档解析、切片、Milvus 入库到检索生成的完整链路。这篇继续往检索层里钻一下：为什么有时候一直调 chunk_size 没用，反而应该先把索引结构和上下文扩展做好。

好耶！

这篇主要讲两个点：结构化索引 和 上下文扩展。
它们解决的是同一个问题：检索要准，给 LLM 的上下文也要够完整。

一、为什么单纯调 chunk 不够

RAG 刚开始做时，最容易陷入一个循环：

这个问题本质上不是参数没调好，而是 检索粒度 和 生成粒度 被绑死了。

如果用大 chunk 入库：

  • 检索时一个块里混了多个主题；
  • 向量相似度容易被不相关内容稀释；
  • top-k 看起来命中了，实际只有其中一两句话相关。

如果用小 chunk 入库：

  • 检索时更容易命中具体句子；
  • 但给 LLM 的上下文太短；
  • 模型可能只看到一句规则，看不到前置条件和例外说明。

RAG 优化不要只盯着 chunk_size。很多时候真正要拆开的是：拿什么做索引，拿什么给模型看。

二、先补上结构化索引

结构化索引是这篇不能漏的部分。

很多 RAG demo 把文档切成一堆文本块，然后直接 embedding 入库。这样能跑，但一旦文档复杂，就容易出问题。

比如一份业务手册里有：

如果只存纯文本 chunk，检索命中“预售”时，系统不一定知道它属于退款规则，还是发货规则。

结构化索引要做的，就是把文档里的结构保留下来。

1. 哪些结构应该进索引

我理解至少要保留这些：

字段 作用
doc_id 标识来自哪份文档，方便更新和删除
section_path 标题路径，比如 售后规则 / 预售订单退款
chunk_id 当前切片 ID
parent_id 所属父节点，用于回填上下文
text 用来做向量检索的小文本
context_text 预先拼好的上下文窗口
source 来源文件、页码或链接
category 业务分类
updated_at 文档更新时间
permission_level 权限过滤

这样做完以后，检索就不是在一堆散文本里盲找，而是在一棵带结构的文档树里找。

句子可以负责精确召回，章节路径和父节点可以负责解释上下文。

2. 结构化索引能解决什么

结构化索引最有用的地方有四个。

第一，能保留标题语义。
很多句子单独看是不完整的，比如：

这句话本身没说是什么到账。
但如果它带着标题路径：

语义就完整很多。

第二，能做元数据过滤。
比如只查售后知识库，只查某个产品线，只查某个租户可见的文档。

第三，能支持递归检索。
先命中句子，再找到所属段落、所属小节，必要时继续向上找父章节。

第四，方便增量更新。
文档变了，可以按 doc_id 或 section_id 删除旧索引，再重新写入，不用全量重建。

结构化索引不是为了把字段堆得很复杂，而是让系统知道：这句话来自哪、属于哪、能不能给当前用户看、命中后应该带回哪段上下文。

三、上下文扩展：小句子召回，大窗口生成

上下文扩展的核心是：一条索引记录里同时保存两种文本。

不要等检索命中以后再临时去拼上下文。
更稳的做法是：索引构建阶段就把上下文窗口准备好。

比如原文是这样的：

索引时可以拆成句子级节点：

sentence_id text
s1 预售订单退款需要先确认商品是否已经发货。
s2 如果商品未发货，用户可提交退款申请。
s3 审核通过后，退款一般会在 3 到 7 个工作日内按原支付路径退回。
s4 如果商品已经发货，需要按普通售后流程处理。

这里的 s1、s2、s3、s4 都会分别作为一条可检索记录，它们的 text 字段各自只保存一句话。
同时，每条记录里再额外保存一个提前拼好的 context_text。比如这四句话本来属于同一个小节，就可以把它们拼成一个窗口：

所以实际存储可以理解成这样：

sentence_id text context_text
s1 第 1 句 第 1 ~ 4 句拼好的上下文
s2 第 2 句 第 1 ~ 4 句拼好的上下文
s3 第 3 句 第 1 ~ 4 句拼好的上下文
s4 第 4 句 第 1 ~ 4 句拼好的上下文

这样用户问：

预售订单退款多久到账？

向量检索可能命中的是 s3 这一句。
但真正交给 LLM 的不是单句 s3，而是这条记录里已经准备好的 context_text。

也就是说：四个句子分别负责被检索命中，拼好的上下文负责让 LLM 生成答案。
命中其中任意一个句子，都可以拿到它绑定的 context_text，再把这个上下文窗口放进 Prompt。

  • 检索时，小句子更精准；
  • 生成时，大上下文更完整。

四、它和 Parent-Child 有什么区别

上一篇里提过 Parent-Child Chunk。
上下文扩展和 Parent-Child 很像，但粒度和实现方式稍微不一样。

方案 检索对象 生成对象 适合场景
Parent-Child child chunk parent chunk 章节 / 段落层级明显的文档
Sentence Window sentence window text 规则、FAQ、手册、短段落知识
结构化索引 结构节点 节点关联上下文 标题、表格、层级很重要的文档

我的理解是：

  • Parent-Child 更像“用小块找大块”；
  • Sentence Window 更像“用一句话找前后几句话”；
  • 结构化索引则是底座，让它们知道父子关系、标题路径和元数据。

实际项目里它们可以一起用。

这样检索会比“固定 800 字符切一块”更可控。

六、为什么它会更精准

上下文扩展不是玄学，它解决的是 RAG 里的一个结构性矛盾。

1. 检索更精准

句子短，语义单一。
用户问“多久到账”，命中的更可能是包含“3 到 7 个工作日”的句子，而不是一个很长的售后章节。

2. 回答更完整

LLM 拿到的不只是命中句，还能看到前置条件：

  • 商品是否发货；
  • 是否需要审核；
  • 是原路退回还是其他方式；
  • 已发货时是否走普通售后。

这样生成答案就不会只答一句“3 到 7 天”，而是能说清楚适用条件。

3. 噪音更少

传统大 chunk 可能混进很多旁支规则。
上下文窗口通常只围绕命中句展开，噪音比直接塞整个章节少。

4. 更好排查问题

如果答案不对，可以直接看：

  • 命中的是哪一句；
  • 它的 context_text 拼得对不对；
  • 标题路径有没有丢；
  • reranker 有没有排错；
  • Prompt 有没有误用资料。

排查链路会清楚很多。

七、上下文窗口怎么取才合适

窗口不是越大越好。

我一般会按文档类型来定：

文档类型 推荐方式
FAQ 命中问题后带答案全文
规则手册 命中句前后 2 ~ 4 句
技术文档 带当前小节，必要时带代码块
合同条款 带当前条款，不跨条款
表格说明 带表头、字段名和当前行
API 文档 带接口标题、参数表和示例

有几个边界要注意：

  • 不要跨标题乱拼；
  • 不要把旧版本和新版本拼在一起；
  • 表格要保留表头；
  • 代码块不要切一半；
  • 权限不同的内容不能拼进同一个窗口；
  • window_text 太长时要截断或摘要。

上下文扩展拼的是“相关上下文”，不是盲目多塞文本。塞得越多，模型越容易被噪音带偏，成本和延迟也会上去。

八、结构化索引和上下文扩展怎么配合

这两个东西最好一起做。

结构化索引解决：

  • 这句话在哪个文档；
  • 属于哪个标题；
  • 关联哪个父节点；
  • 当前用户能不能看；
  • 文档版本是不是最新。

上下文扩展解决：

  • 命中一句话后，给 LLM 哪些上下文；
  • 上下文是否提前拼好；
  • 是否避免临时拼接带来的不稳定；
  • 是否保留来源和标题路径。

九、它和重排序是什么关系

上下文扩展不是重排序的替代品。

比较合理的顺序是：

为什么 rerank 时最好看 context_text？

因为有些句子单独看很像，但上下文一展开就知道不相关。
比如两个句子都写“审核通过后 3 到 7 个工作日”，一个是退款到账，一个是发票审核。只看句子容易混，看标题路径和上下文就能区分。

所以我会把 reranker 当成上下文扩展后的质量门：

  • 初召回负责找候选；
  • 上下文扩展负责补全候选；
  • reranker 负责筛掉看起来像但实际不相关的内容。

十、项目里可以怎么落地

如果我现在要把这个优化加到一个已有 RAG 项目里，会按这个顺序做：

  1. 文档解析时保留标题层级；
  2. 给每个 chunk 增加 section_path、doc_id、parent_id；
  3. 对段落继续拆句；
  4. 给每个句子生成 context_text；
  5. 只对句子 text 做 embedding；
  6. Milvus 里同时存 text 和 context_text；
  7. 检索时命中句子，返回上下文窗口；
  8. reranker 对上下文窗口精排；
  9. Prompt 里带来源、标题路径和内容；
  10. 用评估集对比优化前后的 Recall@K 和答案质量。

十一、评估时看什么

这个优化不能只凭感觉。

建议至少对比三组：

方案 说明
baseline 原始 chunk 检索，直接把 chunk 给 LLM
small chunk 小 chunk 检索，小 chunk 给 LLM
context window 小句子检索，context_text 给 LLM

重点看：

  • 正确片段有没有被召回；
  • 命中的句子是否准确；
  • context_text 是否包含完整答案；
  • reranker 后正确上下文是否排前；
  • 最终回答有没有引用依据；
  • 没答案时是否会拒答；
  • token 成本和延迟有没有明显上升。

如果优化有效，一般会看到：

  • 检索命中更精确；
  • 最终答案更完整；
  • “只答半句”的情况减少；
  • 引用来源更清楚；
  • 坏 case 更容易定位。

十二、写在最后

RAG 检索优化不是一味把 chunk 调大或调小。

更靠谱的方式是把链路拆开：

  • 用结构化索引保留文档层级和元数据；
  • 用小粒度文本做精准召回；
  • 用上下文扩展把预先拼好的 context_text 给 LLM；
  • 用 reranker 再筛一遍真正相关的上下文。

这样做以后，RAG 系统会更像一个会翻资料的人：
先找到关键句，再把它所在的完整语境拿出来，最后基于这段语境回答。
