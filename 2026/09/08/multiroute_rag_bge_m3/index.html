多链路 RAG 文档问答项目：从 BGE-M3 混合检索到 Query Router

Created2026-09-08|Updated2026-09-08|人工智能
|Word Count:5k|Reading Time:16mins|Post Views:
不拒众流，方为江海

最近在整理一个文档问答项目，最开始以为就是“PDF 解析 + 向量入库 + 大模型回答”。真正往下做才发现，RAG 里最麻烦的不是回答，而是检索：问题该怎么拆、编号怎么查准、多路结果怎么合并、什么时候该查知识图谱，什么时候又该去外部搜。

好耶！

这篇按项目复盘写一下：我怎么把一个普通 RAG 问答，慢慢拆成一个 多链路检索系统。

一、先说清楚我要做什么

这个项目我给它的定位是：

面向复杂文档的多链路 RAG 智能问答系统。

简单说，就是用户上传 PDF、产品手册、制度文档、技术文档之后，可以直接问问题。系统不是只用一句话去向量库里搜，而是先判断问题类型，再决定走哪几条检索链路。

大概目标是这几个：

  1. PDF 能解析成 Markdown，并尽量保留标题层级；
  2. 图片、图表里的语义也要能提取出来；
  3. 普通问题能走向量检索；
  4. 编号、型号、条款、错误码这类问题要能精确查；
  5. 复杂问题能拆成多个子问题分别查；
  6. 实体关系问题可以走知识图谱；
  7. 最新信息可以走 MCP 网络搜索；
  8. 多路结果最后统一融合、去重、重排，再给大模型回答。

技术栈大概是：

模块 用什么
工作流 LangGraph
RAG 组件 LangChain
后端服务 FastAPI
文档解析 MinerU
图片语义 Qwen3-VL
向量模型 BGE-M3
向量库 Milvus
重排序 BGE-Reranker
会话记录 MongoDB
文件存储 MinIO
流式输出 SSE
外部搜索 MCP

三、先把层级分清楚

这里还有一个容易混的点：Multi-query、HyDE、BGE-M3、知识图谱、RRF、Reranker 这些词经常被放在一起说，但它们其实不是同一层的东西。

我后来把它们分成了三层：

层级 代表方法 主要作用
查询改写层 Multi-query、Step-back、HyDE 把用户原始问题改写、拆解或扩展，让后面的检索更容易命中
召回方式层 BGE-M3 混合检索、BM25 / sparse、知识图谱、MCP 网络搜索 真正去不同数据源里找候选资料
融合排序层 RRF、BGE-Reranker 把多路召回结果合并、去重、排序，筛出最终上下文

所以它们不是“六个平级的检索算法”。

更准确地说：

比如 Multi-query 不是直接存文档的检索库，它只是把一个复杂问题拆成多个子问题；HyDE 也不是最终答案，而是生成一段假设文档来帮助检索；RRF 和 Reranker 更不是用来“查资料”的，它们负责在资料查回来以后排序。

我觉得把这个层级先分清楚，后面就不会纠结“一个问题到底是选 HyDE，还是选 BGE-M3”这种问题了。因为很多时候它们可以组合：

也就是说：一个方法负责改写，一个方法负责召回，一个方法负责排序。它们不是互斥关系，而是上下游关系。

六、Query Router：问题类型到底怎么判断

这个项目真正开始变清楚，是从 Query Router 开始的。

我不想让每个问题都全链路跑，因为会慢、贵，而且噪声也多。所以需要一个路由器，先判断问题特征，再决定走哪些链路。

我先用了规则版，后面再考虑换成 LLM Router。

大概规则是：

问题特征 走什么链路
普通知识问答 BGE-M3 混合检索
有编号、型号、错误码、条款 sparse / BM25 / 字段过滤
问题很长、多个意图 Multi-query
问题很短、很抽象 HyDE
问“为什么、原理、机制” Step-back
问实体关系、上下游、归属 知识图谱
问最新、实时、价格、版本 MCP 网络搜索

Multi-query 解决的是“问题太复杂”的情况。

所以我会把它拆成：

这个方法很适合：

  • 分别解释几个概念；
  • 问优缺点；
  • 问多个模块如何配合；
  • 一个问题里带好几个意图。

十一、MCP 网络搜索：给本地知识库补实时信息

MCP 这块我一开始也容易理解错。

MCP 不是一种检索算法，它更像是工具连接层。在这个项目里，我可以通过 MCP 接外部搜索、网页、企业系统或者其他数据源。

它适合这种问题：

本地知识库最大的问题是会过期。如果用户问的是最新信息，那只查 Milvus 里的历史文档肯定不够。

所以 Query Router 发现“最新、现在、实时、价格、新闻、版本”这些特征时，就会加一条 MCP 网络搜索链路。

十四、几个实际踩到的问题

1. dense 向量对编号不敏感

编号、SKU、错误码、条款号这些东西，不能只靠 dense embedding。后面必须加 sparse、BM25 或字段过滤。

2. 查询改写不能乱改编号

Multi-query 和 HyDE 都会改写问题，但编号不能被模型改坏。比如 AB-2026-0091 不能改成 AB-2026-0092，也不能省略。

所以我后面会把编号、型号、实体名先抽出来，作为 protected terms 保护住。

3. 多链路不是越多越好

刚开始很容易什么都想加。但链路越多，延迟越高，噪声越多，融合也更麻烦。

所以我最后还是回到 Query Router：简单问题简单查，复杂问题再多路。

4. HyDE 不能直接当答案

HyDE 生成的假设文档只是为了检索。最终答案必须基于真实召回文档，否则还是会变成模型自己编。

5. Reranker 很重要

多路召回后，候选文档质量参差不齐。没有 reranker，LLM 拿到的上下文很容易混，回答就跟着飘。

6. SSE 很有必要

这类多链路流程如果没有进度，用户会觉得系统卡住了。

十五、项目全链路实现

最后这个项目大概可以总结成：

  1. 用 MinerU 把 PDF 解析成 Markdown，保留标题层级；
  2. 用 Qwen3-VL 提取图片、表格和图示语义；
  3. 文档切分时保留 doc_id、section_path、chunk_id、source；
  4. 用 BGE-M3 生成 dense / sparse 向量，写入 Milvus；
  5. MongoDB 保存会话、任务状态和文档元数据；
  6. MinIO 保存原始文档和解析产物；
  7. Query Router 判断问题类型，决定走哪些检索链路；
  8. Multi-query 处理复杂多意图问题；
  9. Step-back 处理原理性问题；
  10. HyDE 处理短 query 和抽象 query；
  11. 知识图谱处理实体关系问题；
  12. MCP 网络搜索处理实时外部信息；
  13. RRF 融合多路召回结果；
  14. BGE-Reranker 对候选上下文精排；
  15. 最后由 LLM 基于上下文生成答案，并通过 SSE 流式返回。

能力上大概覆盖：RAG、检索优化、向量数据库、知识图谱、工作流编排、后端接口、流式输出和工程化调试。

写在最后

这个项目做下来，我最大的感觉是：RAG 不是“把文档丢进向量库”这么简单。

真正难的是让系统知道：

BGE-M3 解决基础语义和关键词召回；BM25 / sparse 解决编号和精确词；Multi-query 解决复杂问题拆解；Step-back 解决原理性问题；HyDE 解决短 query 和长文档的语义差距；知识图谱解决实体关系；MCP 解决外部实时信息；RRF 和 Reranker 负责把多路结果收口。

所以我现在对 RAG 的理解更像是：

检索不是一步动作，而是一套路由、召回、融合、重排的系统工程。

后面如果继续优化，我会优先做三件事：

  1. 把 Query Router 从规则版升级成 LLM + 规则混合版；
  2. 建一套真实 query 评估集，看不同链路的命中率；
  3. 把编号、实体名、条款号做成 protected terms，防止查询改写时被改坏。

行有所思，学有所得。—— AkiTomoyaL
